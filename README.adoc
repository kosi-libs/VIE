= VIE
:toc: macro
:toclevels: 2
:idprefix:
:idseparator: -
:source-highlighter: highlight.js

*Model-View-Intent for Compose Multiplatform — one state flow down, intents up, signals sideways.*

VIE gives a screen three types and a contract between them. A *Model* is the state the view renders.
An *Intent* is a UI event — most often something the user did, but not always. A *Signal* is a
one-off the view should react to but not render — a navigation, a snackbar, a toast. You declare the
three as an interface; a `VIEViewModel` implements it; a `VIEView` renders it. The view only ever
sees the contract, never the ViewModel.

The name is the French translation of MVI: **V**ue **I**ntention **É**tat, built on Compose
**V**iew**M**odels.

.CounterVIE.kt
[source,kotlin]
----
interface CounterVIE : VIE<CounterVIE.Model, CounterVIE.Intent, CounterVIE.Signal> {

    data class Model(val count: Int, val saving: Boolean = false) : VIE.Model

    sealed interface Intent : VIE.Intent {
        data object Increment : Intent
        data object Save : Intent
    }

    sealed interface Signal : VIE.Signal {
        data object Saved : Signal, VIE.Signal.Event          // broadcast to every listener
        data class Error(val message: String) : Signal, VIE.Signal.Effect  // handled once
    }
}
----

.CounterVM.kt
[source,kotlin]
----
class CounterVM(
    private val store: CounterStore,
) : CounterVIE, VIEViewModel<CounterVIE.Model, CounterVIE.Intent, CounterVIE.Signal>(
    firstModel = CounterVIE.Model(count = 0),
    middlewares = listOf(VIELoggingMiddleware("Counter")),
) {
    override suspend fun process(intent: CounterVIE.Intent) {
        when (intent) {
            is CounterVIE.Intent.Increment -> update { copy(count = count + 1) }
            is CounterVIE.Intent.Save -> {
                update { copy(saving = true) }
                store.save(model.count)
                    .onSuccess { signal(CounterVIE.Signal.Saved) }
                    .onFailure { signal(CounterVIE.Signal.Error(it.message ?: "Save failed")) }
                update { copy(saving = false) }
            }
        }
    }
}
----

.Counter.kt
[source,kotlin]
----
@Composable
fun Counter(store: CounterStore) {
    VIEView(newVM = { CounterVM(store) }) { model ->        // `this` is a VIEViewScope
        SignalEffect { signal ->
            when (signal) {
                is CounterVIE.Signal.Saved -> /* … */ Unit
                is CounterVIE.Signal.Error -> /* show snackbar */ Unit
            }
        }
        Column {
            Text("Count: ${model.count}")
            Button(onClick = { post(CounterVIE.Intent.Increment) }) { Text("+") }
            Button(
                onClick = { post(CounterVIE.Intent.Save) },
                enabled = !model.saving,
            ) { Text("Save") }
        }
    }
}
----

No navigation framework, no event bus, no manual `collectAsState`. An interface, a ViewModel, and a
composable that is handed the model and a way to talk back.

== Why VIE

*The contract is an interface.* `CounterVIE : VIE<Model, Intent, Signal>` names the three types once.
The ViewModel is one implementation of that interface; the view function depends on the interface,
not on `CounterVM`. Swapping in a fake for a preview or a test is a different constructor call,
nothing more.

*The view never holds the ViewModel.* Inside `VIEView { }`, the receiver is a
`VIEViewScope<Intent, Signal>` — exactly two members, `post(intent)` and `signalFlow`. No
`modelFlow`, no `update`, no `viewModelScope`, no `process`. A view written as an extension on
`VIEViewScope` (see <<the-view,The view>>) can be rendered against one of VIE's ready-made scopes
with zero Compose ViewModel machinery — see <<previews-and-testing,Previews and testing>>.

*Events and Effects are different delivery channels.* A `Signal` that is a `VIE.Signal.Event` is
broadcast to *every* collector of `signalFlow` that is currently active, and is dropped if there are
none. A `Signal` that is a `VIE.Signal.Effect` goes to *exactly one* collector — useful when two
views observe the same ViewModel and a "navigate back" must fire once, not twice.

*Model updates are serialized.* `update { }` takes a `suspend Model.() -> Model` and hands it to a
single consumer coroutine, then suspends until it has been applied. Two `process` calls racing on
`copy(count = count + 1)` cannot lose an increment.

*Built on `ViewModel`, not beside it.* `VIEViewModel` extends
`androidx.lifecycle.ViewModel`, so `viewModelScope`, `viewModel { }` keying, and Navigation3 entry
scoping all work unchanged. VIE adds the MVI shape; it does not replace the lifecycle.

*Middlewares wrap the flows.* A `VIEMiddleware` intercepts the model, intent and signal flows as
plain `Flow` transformations — logging, filtering, replay — without the ViewModel or the view
knowing.

== Setup

VIE is published as a Kotlin Multiplatform artifact:

.build.gradle.kts
[source,kotlin]
----
kotlin {
    sourceSets {
        commonMain.dependencies {
            implementation("org.kodein.arch.vie:vie:0.1.0")
        }
    }
}
----

VIE depends on Compose runtime, Compose foundation, `lifecycle-viewmodel-compose` and
kotlinx-coroutines as `implementation` dependencies — they are *not* exposed transitively. A Compose
Multiplatform application module already has all of them; a pure-logic module that only declares
`VIEViewModel` subclasses needs at least `kotlinx-coroutines-core` and
`org.jetbrains.androidx.lifecycle:lifecycle-viewmodel-compose` of its own.

Its test helpers — `MockVIE` and `runVMTest` (see <<previews-and-testing,Previews and testing>>) —
live in a separate artifact, so pulling them in never adds test-only dependencies to a production
source set:

.build.gradle.kts
[source,kotlin]
----
kotlin {
    sourceSets {
        commonTest.dependencies {
            implementation("org.kodein.arch.vie:vie-test:0.1.0")
        }
    }
}
----

NOTE: The `group`/`version` publishing coordinates above are the intended ones for both artifacts;
the Gradle build in this repository does not configure Maven publishing yet.

== Core concepts

=== `VIE<Model, Intent, Signal>`

The contract. It is what a view depends on, and what a `VIEViewModel` implements.

[source,kotlin]
----
interface VIE<Model : VIE.Model, Intent : VIE.Intent, Signal : VIE.Signal>
    : VIEViewScope<Intent, Signal> {

    val modelFlow: StateFlow<Model>
    override fun post(intent: Intent)
    override val signalFlow: Flow<Signal>
}
----

The three type parameters are bounded by three marker interfaces — `VIE.Model`, `VIE.Intent`,
`VIE.Signal` — so a stray type cannot slip into the wrong slot.

=== Model

The state the view renders. Always a `data class` — the view relies on its structural equality (to
skip recomposition when an update produces an equal model). A model is always complete: a
`VIEViewModel` is  constructed with a `firstModel`, so `modelFlow` never has to represent "nothing
yet". Model "loading" states are ordinary fields — `val tasks: List<Task>? = null`,
`val saving: Boolean = false`.

[source,kotlin]
----
data class Model(
    val count: Int,
    val saving: Boolean = false,
) : VIE.Model
----

=== Intent

A UI event — most often something the user did, but not always (a lifecycle callback, a timer firing
in the view, an incoming deep link). Sent from the view with `post(intent)`. Model it as a
`sealed interface` so `process` can `when` over it exhaustively.

[source,kotlin]
----
sealed interface Intent : VIE.Intent {
    data object Increment : Intent
    data class SetName(val name: String) : Intent
}
----

A screen that takes no input at all can use the built-in `VIE.Intent.None` as its `Intent` type — it
has a private constructor and cannot be instantiated, so `post` becomes uncallable. It is aliased
`NoIntent` — import it directly and use the bare name: `VIE<Model, NoIntent, Signal>`.

=== Signal

A one-off the view should act on but not render. Every concrete signal must also pick a *delivery
kind* by implementing one of:

[cols="1,3",options="header"]
|===
| Kind | Delivery

| `VIE.Signal.Event`
| Broadcast to *every* active collector of `signalFlow`. Emitted with no collector, it is dropped
  (there is no replay buffer). Use for things every listener cares about: "data saved", "logged
  out".

| `VIE.Signal.Effect`
| Delivered to *exactly one* collector. If several views observe the same ViewModel, an `Effect`
  reaches whichever one collects it first. Use for one-shot navigation and other actions that must
  not happen twice.
|===

[source,kotlin]
----
sealed interface Signal : VIE.Signal {
    data object LoggedOut : Signal, VIE.Signal.Event
    data class ShowError(val message: String) : Signal, VIE.Signal.Effect
}
----

A screen with nothing to signal can use `VIE.Signal.None` as its `Signal` type. It is aliased
`NoSignal` — import it directly and use the bare name: `VIE<Model, Intent, NoSignal>`.

== The ViewModel

`VIEViewModel` is the abstract base. Subclass it, pass the first model and any middlewares up, and
implement `process`.

[source,kotlin]
----
abstract class VIEViewModel<Model : VIE.Model, Intent : VIE.Intent, Signal : VIE.Signal>(
    firstModel: Model,
    middlewares: List<VIEMiddleware<Model, Intent, Signal>> = emptyList(),
) : ViewModel(), VIE<Model, Intent, Signal>
----

[cols="1,3",options="header"]
|===
| Member | Purpose

| `abstract suspend fun process(intent: Intent)`
| Called for every posted intent, one at a time, on `viewModelScope`. Long or parallel work should
  be launched into `viewModelScope` explicitly rather than blocking the intent stream.

| `suspend fun update(update: suspend Model.() -> Model)`
| Atomically replaces the model. Serialized against all other `update` calls; returns once applied.

| `protected val model: Model`
| The current model — shorthand for `modelFlow.value`.

| `suspend fun signal(signal: S) where S : Signal, S : VIE.Signal.Type`
| Emits a signal. The bound forces `S` to be an `Event` or an `Effect` — a signal type that picked
  neither will not compile at the call site.

| `final override fun post(intent: Intent)`
| Feeds an intent into the pipeline. Provided; not overridable.
|===

.CounterVM.kt
[source,kotlin]
----
override suspend fun process(intent: CounterVIE.Intent) {
    when (intent) {
        CounterVIE.Intent.Increment -> update { copy(count = count + 1) }
        CounterVIE.Intent.Reset     -> update { copy(count = 0) }
    }
}
----

=== Feeding a Flow into the model or a signal

Two helpers collect an external `Flow` straight into the ViewModel. They are declared with a
`context` parameter, so they are called from inside a `VIEViewModel` (typically an `init` block or a
`viewModelScope` coroutine):

[source,kotlin]
----
// context(vm: VIEViewModel<Model, *, *>)
suspend fun <Model, T> Flow<T>.collectToModel(update: suspend Model.(T) -> Model)

// context(vm: VIEViewModel<*, *, Signal>)
suspend fun <Signal, T> Flow<T>.collectToSignal(convert: suspend (T) -> Signal)
    where Signal : VIE.Signal, Signal : VIE.Signal.Type
----

.TaskListVM.kt
[source,kotlin]
----
init {
    viewModelScope.launch {
        taskRepository.flow().collectToModel { tasks -> copy(tasks = tasks) }
    }
}
----

== The view

`VIEView` is the single entry point. It creates (and remembers, keyed) the ViewModel, collects
`modelFlow` as Compose state, and invokes `content` with the current model and a
`VIEViewScope` receiver.

[source,kotlin]
----
@Composable
inline fun <reified Model : VIE.Model, Intent : VIE.Intent, Signal : VIE.Signal> VIEView(
    crossinline newVM: () -> VIEViewModel<Model, Intent, Signal>,
    key: String? = null,
    content: @Composable VIEViewScope<Intent, Signal>.(Model) -> Unit,
)
----

Inside `content`, `this` is a `VIEViewScope<Intent, Signal>`:

[source,kotlin]
----
interface VIEViewScope<Intent : VIE.Intent, Signal : VIE.Signal> {
    fun post(intent: Intent)
    val signalFlow: Flow<Signal>
}
----

=== `SignalEffect`

React to signals with the `SignalEffect` composable — it collects `signalFlow` for the lifetime of
the composition:

[source,kotlin]
----
SignalEffect { signal ->
    when (signal) {
        is Signal.LoggedOut  -> navController.navigate("login")
        is Signal.ShowError  -> snackbarHostState.showSnackbar(signal.message)
    }
}
----

=== Views as extension functions

Splitting the wiring from the layout keeps the layout testable. The demo does this everywhere: a
thin `@Composable` that calls `VIEView`, and a second `@Composable` extension on `VIEViewScope`
that only takes `model` plus plain callbacks.

[source,kotlin]
----
@Composable
fun TaskList(goToTask: (Uuid) -> Unit) {
    VIEView(newVM = { TaskListVM(/* … */) }) { model ->
        TaskList(model = model, goToTask = goToTask)   // extension below
    }
}

@Composable
fun VIEViewScope<TaskListVIE.Intent, TaskListVIE.Signal>.TaskList(
    model: TaskListVIE.Model,
    goToTask: (Uuid) -> Unit,
) {
    // renders `model`, calls `post(…)`, uses `SignalEffect { }` — no ViewModel in sight
}
----

The second function can be exercised in a `@Preview` against an `EmptyVIE` or a test against a
`MockVIE` — see <<previews-and-testing,Previews and testing>>.

== Previews and testing

A view written as a `VIEViewScope` extension (see <<views-as-extension-functions,Views as extension
functions>>) needs nothing more than a `VIEViewScope` to render — no `VIEViewModel`, no
`viewModel { }` keying, no lifecycle. VIE ships two ready-made scopes for exactly that, one per job:
`EmptyVIE` to look at the layout, `MockVIE` to assert on it.

`EmptyVIE` lives in `commonMain` of the `vie` artifact itself, so it is reachable from `@Preview`
functions in a main source set, not just from tests. `MockVIE` — along with `runVMTest`, for testing
the ViewModel side — lives in the separate `vie-test` artifact (see <<setup,Setup>>), so a
production source set never has to depend on it.

=== Previews

`EmptyVIE<Intent, Signal>` is a `VIEViewScope` with nothing behind it: `post` discards the intent,
and `signalFlow` is an always-empty `Flow`, so a `SignalEffect { }` in the view never fires. It
carries no model — unlike `MockVIE` below, there is nothing to seed — so the model goes to the
view's own `model` parameter, once:

[source,kotlin]
----
@Preview
@Composable
fun CounterPreview() {
    EmptyVIE<CounterVIE.Intent, CounterVIE.Signal>().Counter(
        model = CounterVIE.Model(count = 3),
    )
}
----

`@Preview` needs `org.jetbrains.compose.ui:ui-tooling-preview` on the classpath (and
`org.jetbrains.compose.ui:ui-tooling` as a `runtimeOnly` dependency for the IDE/tooling to render
it) — see `demo/demo-shared/build.gradle.kts` for a module that declares both alongside VIE.

=== Testing a view with `MockVIE`

`MockVIE<Model, Intent, Signal>` (from `vie-test`) is a full `VIE` implementation, not just a
`VIEViewScope`: it holds a model, records every posted intent, and lets a test emit signals — built
for assertions, not for previews. (It *would* work as a preview receiver too, since `VIE` extends
`VIEViewScope`, but it needs a seeded model and records intents nobody reads; `EmptyVIE` above is
the right tool when nothing has to be recorded or driven.)

[cols="1,3",options="header"]
|===
| Member | Purpose

| `MockVIE(model)`
| Constructor. Seeds `modelFlow` with the model to render.

| `val model: Model`
| The current model — shorthand for `modelFlow.value`.

| `override val modelFlow: MutableStateFlow<Model>`
| Mutable: assign to it to re-render the view with a new model.

| `val intentsChannel: ReceiveChannel<Intent>`
| Every intent the view has posted, in the order it posted them.

| `override fun post(intent: Intent)`
| Records the intent into `intentsChannel`. Nothing processes it — no model update, no signal.

| `override val signalFlow: MutableSharedFlow<Signal>`
| Mutable: `emit` into it (or call `signal(…)` below) to drive the view's `SignalEffect { }`.

| `fun signal(signal: Signal)`
| Non-suspending shorthand for `signalFlow.tryEmit(signal)`, handy from a test body.

| `fun pendingIntents(): List<Intent>`
| Drains `intentsChannel` and returns everything posted since the previous call, in order;
  `emptyList()` if nothing was posted.
|===

`pendingIntents()` turns a rendered view into something a test can assert on without touching a
`VIEViewModel`:

[source,kotlin]
----
val model = CounterVIE.Model(count = 0)
val vie = MockVIE<CounterVIE.Model, CounterVIE.Intent, CounterVIE.Signal>(model)

// render the view against `vie`, then simulate the user tapping "+" twice …
vie.post(CounterVIE.Intent.Increment)
vie.post(CounterVIE.Intent.Increment)

assertEquals(
    listOf(CounterVIE.Intent.Increment, CounterVIE.Intent.Increment),
    vie.pendingIntents(),
)
----

`pendingIntents()` *drains* — it is not an accumulating log. Each call returns only what was posted
since the previous call; calling it twice in a row without an intervening `post` returns
`emptyList()` the second time.

`modelFlow` and `signalFlow` are the mutable counterparts of the read-only members `VIE` exposes,
so a test can also drive the view from the other direction: assign `modelFlow.value` to re-render
with a new model, or `signalFlow.emit(…)` / `signal(…)` to check the view's `SignalEffect` reaction.
`signalFlow` is a buffered `MutableSharedFlow` with no *replay*: a signal sent before any collector
has started is held in the buffer and delivered once one does, but it is not replayed to a
*second*, later collector — send it after the view has composed.

`MockVIE` replaces the ViewModel entirely: there is no `process`, no middleware, no
`viewModelScope`. Testing how a `VIEViewModel` handles an intent — the `process` side — is a
separate, ordinary unit test against the `VIEViewModel` subclass itself; `runVMTest` below exists to
make that straightforward.

=== Testing a `VIEViewModel` with `runVMTest`

A `VIEViewModel` subclass is a plain class: construct it directly with whatever real or fake
collaborators the test needs, no DI container required. Three of its mechanics make that more than
a bare constructor call, though — all handled by `runVMTest` (from `vie-test`):

* `modelFlow` is `stateIn(viewModelScope, SharingStarted.Lazily, …)`, so it only advances state
  while something collects it.
* `signalFlow` has no replay, so a signal emitted with nobody collecting is lost.
* `viewModelScope` resolves `Dispatchers.Main` the first time it is touched — typically in
  `init { }` — so `Dispatchers.Main` must already be a `TestDispatcher` *before* the view model is
  constructed, for its (and any repository's) `delay(…)` calls to run on virtual time instead of
  wall-clock time.

`runVMTest` builds the view model inside a `kotlinx.coroutines.test.runTest { }` with all three
already arranged: model and signal collectors are running before `newVM` returns, and `block` gets
the view model plus every signal collected so far.

[source,kotlin]
----
@Test
fun save_updatesModelAndSignalsSaved() = runVMTest(
    newVM = { CounterVM(FakeCounterStore()) },
) { vm, signals ->
    vm.post(CounterVIE.Intent.Save)
    advanceUntilIdle()

    assertEquals(CounterVIE.Signal.Saved, signals.single())
    assertEquals(false, vm.modelFlow.value.saving)
}
----

`newVM` and `block` both run with `TestScope` as their receiver, so `advanceTimeBy`, `runCurrent`
and `advanceUntilIdle` are all in scope directly, no `this@runTest` needed. The view model is
cleared once `block` returns, cancelling `viewModelScope`.

== Middlewares

A `VIEMiddleware` intercepts each of the three flows. Every method defaults to identity, so override
only what you need:

[source,kotlin]
----
interface VIEMiddleware<Model : VIE.Model, Intent : VIE.Intent, Signal : VIE.Signal> {
    fun interceptModels(flow: Flow<Model>): Flow<Model> = flow
    fun interceptIntents(flow: Flow<Intent>): Flow<Intent> = flow
    fun interceptSignals(flow: Flow<Signal>): Flow<Signal> = flow
}
----

`VIELoggingMiddleware(name)` ships in the box — it prints every model, intent and signal, plus
`START` / `END` markers, prefixed with `name`.

[source,kotlin]
----
VIEViewModel(
    firstModel = Model(count = 0),
    middlewares = listOf(
        VIELoggingMiddleware("Counter"),
        MetricsMiddleware(),
    ),
)
----

*Order.* The list is folded from the end, so the *last* middleware wraps the raw source flow and the
*first* sits closest to the ViewModel/view. Above, `MetricsMiddleware` sees the source values;
`VIELoggingMiddleware` sees whatever `MetricsMiddleware` passed through.

== Supported platforms

`vie` is a Kotlin Multiplatform library targeting:

* *JVM*
* *iOS* — `iosArm64`, `iosSimulatorArm64`
* *JS* — browser
* *Wasm/JS* — browser

The library declares no Android target of its own; an Android application consumes it through a
shared Compose Multiplatform module that does (as `demo/demo-android` does through
`demo/demo-shared`).

== Demo

`demo/demo-shared` is a full task-list application built on VIE — two screens
(`TaskListVIE` / `EditTaskVIE`), each with its contract, ViewModel and view, over an async
repository. It runs on every target:

[source,bash]
----
./gradlew :demo:demo-desktop:run                              # JVM desktop window
./gradlew :demo:demo-desktop:jsBrowserDevelopmentRun          # JS in the browser
./gradlew :demo:demo-desktop:wasmJsBrowserDevelopmentRun      # Wasm/JS in the browser
./gradlew :demo:demo-android:installDebug                     # Android device / emulator
----

iOS runs from the Xcode project in `demo/demo-ios/kosi-vie-demo`.

The demo wires its ViewModels with https://github.com/kosi-libs/Inara[Inara] (`@DIModule` in
`business/AppModule.kt`, `@DIFactory` in `vie/vm/VMFactory.kt`) — VIE itself has no dependency on any
DI framework, and `VIEViewModel` subclasses are plain constructors.
